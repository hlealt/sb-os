🎯 Core Module (PARA)

Foundation layer: vault initialization, session documentation, context injection, and life-planning reviews across weekly, monthly, and quarterly horizons.

/sb-onboarder Command
▼

Trigger: User runs /sb-onboarder after fresh sb-os install or to resume a paused session.

Purpose

Post-install interactive onboarding: orient the user to sb-os, populate PARA structure, optionally build Home dashboard, optionally pitch RBTV plugin.

Complete Workflow (7 Steps + Resume)

  1. Step 01 — Orient: Welcome user, teach PARA/periodic-notes/workbench/tags/wiki/life-planner/context-injection concepts using data/concept-primer.md. Pause after each block for comprehension. Write initial onboarder_state to sb-os.json.
  2. Step 01b — Continue/Resume: Check existing onboarder_state. If completed, show resume menu (Resume/Restart/Jump-to-Home/Jump-to-Finalize/Exit). If fresh, proceed to Step 02.
  3. Step 02 — Discover Domains: Present life-domain inspiration table from data/life-domain-inspiration.md. Walk through row-by-row. Capture user's domain list into domains_proposed. Confirm and update state.
  4. Step 03 — Areas: For each domain, create folder 2-areas/area-{domain}/ and index file with user-provided description. Create area-{domain}-tasks.md ONLY for areas with elicited tasks (never empty task files). Invoke sb-vault-ops before writing. Run sb-vault-integrity post-op. Update state with areas_created.
  5. Step 04 — Projects: Elicit current bounded efforts via concrete prompts (goal with finish line, ship in 90 days, life milestone, work deliverable, stalled work). Reality-check: if >5 projects, ask which are truly active. Create 1-projects/{project}/ folders and indexes. Create {project}-tasks.md ONLY for projects with elicited next actions. Invoke sb-vault-ops and sb-vault-integrity. Update state.
  6. Step 05 — Resources (conditional): If resources_surfaced is empty, skip silently. Otherwise, re-confirm each resource candidate, map to destination (tools/prompts/repos/articles/other), batch-confirm, write via sb-vault-ops. For repos and wiki content, print next-step commands instead of writing directly. Update state with resolved destinations.
  7. Step 06 — Home (optional): Offer to build Home.md dashboard. If yes: print plugin requirements (Dataview + Templater), read ideas/home-dashboard.md, present all six capability families verbatim (Temporal, Intent, Tasks, Recurring, Lifecycle, Interaction), user picks 2-4 across families, generate Home.md with dynamic blocks and fallback text, invoke sb-vault-ops and sb-vault-integrity. Update state with home_built: true.
  8. Step 07 — Finalize: Elicit user-extension routing rules (where articles go, topic-specific catalogs). Append to root CLAUDE.md OUTSIDE sb-os marker block under "Personal Routing Rules". Market RBTV with exact install commands (git clone + python install.py). Print summary of created artifacts. Mark completed_at in state.

State Management

onboarder_state in sb-os.json persists across sessions:

{
  "started_at": "ISO-8601",
  "last_step": "step-NN-name",
  "completed_steps": ["step-01-orient", ...],
  "domains_proposed": ["area-finance", ...],
  "areas_created": ["2-areas/area-finance", ...],
  "projects_created": ["1-projects/project-name", ...],
  "resources_surfaced": [{name, type, destination}, ...],
  "home_built": false,
  "rbtv_marketed": false,
  "completed_at": null
}

Critical Rules

  • NEVER load multiple step files at once — load and execute sequentially.
  • NEVER skip a step or merge two steps.
  • ALWAYS update state before loading next step.
  • ALWAYS halt at menus and wait for user input.
  • NEVER write inside .user/ — state lives in sb-os.json.
  • Show proposals first; require explicit confirmation before writing.
  • Invoke sb-vault-ops before ANY vault write; invoke sb-vault-integrity post-op.
/sb-archivist Command
▼

Trigger: User runs /sb-archivist at end of session to document work or sweep completed tasks.

Purpose

Document all session work into the rolling work-log file (completed actions, decisions, rejected alternatives, discoveries, files read). On fresh runs with no session work, sweep done tasks from vault task files into date-correct work logs.

Two Modes

Mode 1: Session Documentation (when work exists)

  1. Read template: Read para/templates/work-log.md for canonical format and section layout.
  2. Check today's log: Read .user/runtime/state/work-log.md:
    • If date matches today → append (do NOT overwrite)
    • If date is older → move to .user/runtime/state/work-log-archive/{YYYY-MM-DD}-work-log.md, then create fresh log
    • If missing/empty → create fresh from template
  3. Review session: Scan entire conversation history and extract: files read/created/edited/deleted, decisions made, alternatives considered, collaborative refinements, discoveries, tasks completed.
  4. Populate sections: Write to appropriate sections per template:
    • Completed: - [x] {action} ✅ YYYY-MM-DD
    • New Tasks Created: - {task} → 📅 YYYY-MM-DD in [[{file}]]
    • Updates: Free-form narrative bullets
    • Key Decisions: Table rows with decision, choice, rationale
    • Rejected Alternatives: Table rows with option, why rejected, trade-off
    • Discoveries: - YYYY-MM-DD | {discovery}
    • Files Read: Table rows with file, why, key insight
  5. Update metadata: Update last_updated in frontmatter to current timestamp.

Mode 2: Done-Task Sweep (fresh-session runs only)

Runs ONLY when session produced no documentable work.

  1. Find done tasks: Content-search 1-projects/ and 2-areas/ for - [x] lines in *-tasks.md files.
  2. Extract blocks: A swept block = top-level - [x] line plus ALL indented continuation lines. Preserve exactly — never reformat.
  3. Route by date: Read ✅ YYYY-MM-DD marker. Earlier than today → archive file. Today or missing → today's log.
  4. Create missing archives: If target archive file missing, create with frontmatter and ## Completed section.
  5. Append grouped: Inside target's ## Completed, group under ### Swept from [[{file-name}]]. Skip if already logged.
  6. Remove from source: Delete each swept block from its task file. Touch nothing else.
  7. Update and report: Update last_updated in every touched work-log. Report one-line summary in chat.

Critical Rules

  • Do NOT summarize in chat — write to file and confirm.
  • Do NOT skip reading template — format is authoritative.
  • Do NOT collapse rich content into Updates — populate full tables for decisions/refinements.
  • Do NOT sweep open (- [ ]) tasks or checked sub-items of open tasks.
  • Do NOT run sweep when session produced documentable work — document the session; done tasks wait for next fresh run.
/sb-inject-context Command
▼

Trigger: User runs /sb-inject-context to manage per-workflow context files.

Purpose

Interactive CRUD for workflow context injection entries. Creates, updates, and deletes YAML context files under the configured user-context root (resolved from sb-os.json → user_context_root; default .user/context/).

Entry Point Menu

Context Injection Manager
→ [C] Create entry
→ [U] Update entry
→ [D] Delete entry

Create Entry Flow

  1. Resolve target: Ask user which workflow and where to inject context. Read workflow entry and step files. Map user description to correct step file. Confirm mapping.
  2. Check existing: Resolve context YAML path: {user_context_root}/{workflow-path}/{step}.yaml. Show current entries if file exists.
  3. Define entry: Collect interactively:
    • Name: Human-readable label
    • Type: file | script | url | text | mcp
    • Mode: read (default) | write | read-write
    • Instruction: What agent should do with content (1-3 sentences)
  4. Type-specific fields:
    • file: path, glob, select, count, sections
    • script: command, args
    • url: url
    • text: content
    • mcp: server, tool, params
  5. Review & confirm: Show complete YAML entry. Ask: "Add this entry? [Y/N]"
  6. Write: Create directory if missing. Append to existing YAML or create new with context: key.
  7. Continue: Ask: "Add another entry? [Y/N]" → loop or return to menu.

Update & Delete Flows

Both follow same target resolution, then show numbered entry list. User selects entry to update/delete. For update: show current values, collect new values, confirm, write. For delete: confirm, remove from YAML (delete file if empty).

sb-life-planner Skill
▼

Trigger: User initiates a personal review session (weekly, monthly, or quarterly).

Purpose

Run the life-planning workflow — weekly, monthly, or quarterly review — when the user initiates a personal review session.

Dispatcher Flow

  1. Present options: Ask user which review to run:
    • Week: Weekly review
    • Month: Monthly review
    • Quarter: Quarterly review
  2. Load workflow: Based on user choice, load and execute corresponding workflow file:
    • Week → weekly-review/weekly-review.md
    • Month → monthly-review.md
    • Quarter → quarterly-review.md
  3. Context overrides: If context YAML provides option.week.description, option.month.description, or option.quarter.description, use those instead of English defaults.

Weekly Review (Deep Dive)

Purpose: Close the ending week and plan the next one, ensuring the vault Home reflects exactly what was planned.

Session Log

Created at start of review. Default path: 0-periodic-notes/weekly/{week}-session-log.md. Tracks decisions, tasks mentioned, name corrections, priorities, habits inventory, and daily inventory for reconciliation.

Week Boundaries

Default first day: Monday. If context YAML provides config.week.start-day, use that. Closing week/planning week determined by today's day-of-week.

8-Step Flow

Step File Purpose
01 step-01-close-week.md Init + retrospective + session log creation. Dispatch sub-agents to inventory each daily note (one sub-agent per daily). Collect habits and daily inventory tables.
02 step-02-axis-context.md Life axis coverage check + therapy/psychiatry context reading
03 step-03-intention.md "Good week" reflection without bias — clean room, objective-driven
04 step-04-calendar.md Calendar reading (past + future)
05 step-05-route-dailies.md Review and route daily note content
06 step-06-context.md Vault scan + cross-reference with intentions + chronic stragglers + axis tracking
07 step-07-plan-and-write.md Daily distribution with immediate vault writing
08 step-08-verify.md Triple check (5 verifications) + archive session log

Context Blocks & Resumability

Weekly review is split into three context blocks:

  • Block A (Steps 01-03): Reflective/strategic. Heavy personal context, discussion, challenging. Reads therapy/self-knowledge/goals inputs.
  • Block B (Steps 04-05): Calendar + routing. Reads weekly note from A, session log. Calendar events, daily notes for routing.
  • Block C (Steps 06-08): Planning + verification. Reads weekly note (A+B), session log (with daily inventory from B). Vault task files for planning.

At each block boundary (03→04 and 05→06), user starts a fresh session. Agent reads stepsCompleted in weekly note frontmatter and resumes from next step.

Monthly & Quarterly Reviews

Monthly: Closes ending month, sets next-month intentions across life areas. Synthesizes patterns from weekly notes, identifies neglected axes.

Quarterly: Strategic horizon. Closes quarter, sets next-quarter intentions. Synthesizes trajectory from monthly reviews, evaluates life-area shifts.

📚 Wiki Module

Knowledge-base layer: Karpathy-style raw/wiki/sources/topics/concepts/entities structure with ingest, query, lint, and topic-creation workflows.

/sb-wiki-ingest Command
▼

Trigger: /sb-wiki-ingest <slug> (interactive) or /sb-wiki-ingest silent <slug> (non-interactive for orchestrators).

Purpose

Two-stage Karpathy-style ingest of a raw source into the wiki. Distills source into wiki pages, updates entity/concept pages with append-only protection, creates stubs, detects candidate-topic triggers, updates indexes, and presents Stage 1 + Stage 2 checkpoints.

Invocation Forms

Form Behavior
/sb-wiki-ingest <slug> Default (interactive). Full 11-step flow with both checkpoints presented to user.
/sb-wiki-ingest silent <slug> Silent (non-interactive). Runs steps 0–9 unchanged, auto-resolves step 10 to fixed defaults, SKIPS step 11, returns structured summary.

11-Step Flow

  1. Load extensions: Read sb-os.json → wiki_extensions. Merge extension page-types, frontmatter-schemas, section-menus into active rule set.
  2. Load purpose lens (optional): Read optional {wiki_root}/purpose.md. If present, load focus areas, down-weight signals, quality bar, out-of-purpose list. Modulates discretionary surfaces only.
  3. Load questions registry (optional): Read optional {wiki_root}/questions.md. Parse open questions for answer-scan at Stage 1.
  4. Read raw file: Resolve <slug> against {wiki_root}/raw/. Handle PDF sources natively (read every page). Determine source kind: article | paper | podcast | study | repo.
  5. PDF title-conformance (PDF only): Compute {title-slug} from document title. If stem differs, rename PDF to {title-slug}.pdf. Check for text-twin {title-slug}.md — if absent, extract text twin using pypdf. Preserve both files.
  6. Create source page: Write {wiki_root}/wiki/sources/{origin}/{title-slug}.md with frontmatter, sections, and citations per wiki schema. Classify source per purpose lens (in-focus/peripheral/off-purpose).
  7. Update entity/concept pages: For every entity/concept mentioned, append new findings to existing pages with append-only protection. Never overwrite.
  8. Create stubs: For mentioned but non-existent entities/concepts, create stub pages per stub-policy rules.
  9. Detect candidate topics: Apply candidate-topic-triggers rules. If triggers fire, create candidate-topic entry in {wiki_root}/log.md.
  10. Update indexes: Update/create sources/{origin}/{origin}.md index and leaf indexes (concepts.md, entities.md, topics.md).
  11. Stage 1 commit gate: Present all proposed changes (new pages, updates, stubs, candidate topics, index changes) in a structured table. User confirms or rejects. On accept, commit changes to disk.
  12. Stage 2 reflection (optional): After commit, offer optional reflection pass to refine synthesis or add cross-links. User can skip.

Retrieval Tiers

Semantic search (via sb-wiki-search.py) runs on every query when available. Deterministic baseline (leaf-index scoring + grep) is the floor when semantic tier unavailable. Semantic tier NEVER decides mechanical fires — topic detection, stub rules, and trigger detection stay fully deterministic.

Write-Surface Contracts

  • Thesis pages are scribe-only — NEVER create/edit wiki/theses/.
  • Below-bar claims written to source page only, never entity page.
  • File routing via designated capture tool only.
  • Screenshot images → raw/_assets/ + embedded in place.
/sb-wiki-ingest-all Command
▼

Trigger: /sb-wiki-ingest-all [origin] (no arg = all origins, optional arg = single origin for test run).

Purpose

Backfill the wiki: ingest every non-ingested raw source via batched Opus subagents, then lint. Pure orchestrator — per-source logic lives in /sb-wiki-ingest.

Orchestration Contracts

Contract Rule
Token budget Subagent batch MUST NOT exceed 50,000 estimated source tokens. Single source exceeding 50k becomes its own batch.
Same-origin serialization Batches of SAME origin run STRICTLY sequentially — never two at once.
Cross-origin parallelism Batches of DIFFERENT origins MAY run in parallel, capped at 5 concurrent subagents.
Non-interactive ingest Subagents invoke /sb-wiki-ingest silent <slug> per file. NO subagent pauses for input.
Model Subagents run on Opus (user-requested for ingest quality).
No mid-run topic pages Subagents NEVER create topic pages mid-run. Proposed topics deferred to final lint pass.
Single git commit NO git command during ingestion. Orchestrator creates EXACTLY ONE git commit at end of run.

Execution Flow

  1. Discover non-ingested sources: Run python {sb_os_path}/wiki/scripts/sb-wiki-ingest-all-manifest.py --report {wiki_root}/ingest-all-manifest.json. Read JSON manifest with per-file token estimates.
  2. Build batches: Group files by origin. Within each origin, batch by token budget (50k max per batch). Preserve same-origin serialization order.
  3. Schedule waves: Organize batches into waves respecting cross-origin parallelism cap (5 concurrent).
  4. Dispatch subagents: For each batch, spawn a subagent running /sb-wiki-ingest silent <slug> per file. Collect structured per-file status.
  5. Final lint: After all ingestion completes, run /sb-wiki-lint to heal cross-origin duplicates, update indexes, surface findings.
  6. Git commit: Stage and commit all changes with single git commit message summarizing ingest scope and file count.
  7. Report: Return summary: total files ingested, per-origin counts, any failures, lint findings.
/sb-wiki-query Command
▼

Trigger: /sb-wiki-query <question> (free-form natural-language question).

Purpose

Synthesize an answer to a user question from the wiki — parse question, pick candidates deterministically, run hybrid semantic+keyword retrieval on EVERY query when available, follow wikilinks for depth, synthesize with inline citations, present answer, offer to file result back as a wiki page.

7-Step Execution Flow

  1. Load questions registry: Read optional {wiki_root}/questions.md. Decide whether register-as-open-question offer fires at Step 6 on miss.
  2. Parse question: Classify candidate page types (Concept | Entity | Topic). Extract keywords. Build candidate-types and keywords sets.
  3. Pick candidates (deterministic layer): If semantic tier available: pick directly without leaf-index reads (direct hits + filename matching), then ALWAYS run semantic search. If tier unavailable: read leaf indexes, score by keyword match, pick top candidates.
  4. Semantic retrieval: When available, run python {sb_os_path}/wiki/scripts/sb-wiki-search.py search "<question>" --k 8. Union results with deterministic picks.
  5. Follow wikilinks: For each picked page, follow wikilinks for depth (bounded). Gather related content.
  6. Synthesize answer: Compose answer from gathered content with inline wiki/source citations. Present answer to user. Offer to file back as Concept/Entity/Topic page or register as open question (on miss).
  7. File back (optional): If user accepts, invoke sb-wiki-create-topic or create Concept/Entity page per user intent.

Retrieval Tiers

Semantic search runs on EVERY query when available (unioned with deterministic picks). Leaf-index scoring + grep/ripgrep are deterministic floor. Helper failure NEVER aborts query — drop to floor and continue.

/sb-wiki-lint Command
▼

Trigger: /sb-wiki-lint (no arguments). Walks entire wiki and raw trees in one pass.

Purpose

Health check + index maintenance for raw/ and wiki/ — detect stubs, orphans, unresolved Disputed callouts, aging candidate-topics, broken wikilinks; auto-apply index sync writes; present read-only findings to user.

Read-Mostly Behavior

Auto-applied writes are SCOPED to index sync only. Subdivision execution, PDF title-conformance rename, questions answer-sweep, and broken-link fixes are USER-GATED (only on explicit accept at step 9).

9-Step Execution Flow

  1. Run deterministic helpers: Execute helper scripts for deterministic index-row + footnote work. Consume JSON report.
  2. Detect structural issues: Walk raw/ and wiki/ trees. Detect: orphaned pages, broken wikilinks, unresolved Disputed callouts, aging candidate-topics.
  3. Auto-sync writes: Re-sync wiki sources My take column from each source page. Renumber footnotes (safe bijections only). Create missing raw/wiki indexes.
  4. Fill index descriptions: Extract lead definition sentence from each concept/entity page. Fill Description cells in leaf indexes. Report weak pages.
  5. Type-tag sync: Append each page's type: value to tags: frontmatter when absent (append-only). Add type: index + tags: [index] to index files missing type:.
  6. Prune spent entries: Delete candidate-topic/candidate-mention entries from log.md whose page now exists. Delete retired history entries. Prune promoted/retired entries from questions.md.
  7. Regenerate open-gaps: Overwrite open-gaps.md wholesale with cross-wiki aggregate of all open questions. ALWAYS emitted (empty-state file when nothing to aggregate).
  8. Present findings: Show user all detected issues, proposed fixes, and user-gated execution options (subdivisions, PDF renames, question answer-sweep, link fixes, missing-page stubs, topic graduation).
  9. Execute user-gated changes: On user accept, execute: folder subdivisions, PDF title-conformance renames, question answer-sweep, broken-link rewrites, missing-page stub authoring, topic graduation via sb-wiki-create-topic.

Out of Scope: raw/_assets/ is user-maintained via Obsidian's "Download attachments" command. Lint NEVER reads/writes/walks this folder.

/sb-tutor Command
▼

Trigger: User runs /sb-tutor to start a learning session on any subject.

Purpose

Private tutor that delivers knowledge in small, digestible pills through guided, personalized learning paths.

Persona & Tone

Warm, patient, encouraging — like a favorite mentor. Celebrate small wins. When student struggles, reassure that difficulty is normal. Conversational, not academic. Light humor when it fits. Never condescending.

Activation Flow

  1. Load boot rules: Read ./step-01-boot.md — load all behavioral rules, first-run gates, pill-based teaching constraints.
  2. Check for study topic: If student provided a topic → follow standard flow immediately.
  3. Check context injection: If invoked with NO topic and context injection provides study topics → present them and ask what they want to learn today.
  4. Ask for topic: If invoked with NO topic and no context available → ask student what they want to learn.
  5. Continuous pill mode: There is no step 02 — tutor runs continuously in pill mode, delivering knowledge in small, digestible chunks with pauses after each response.

Teaching Protocol

  • Pill-based delivery: Pause after each response for student input. Never deliver large blocks of knowledge.
  • Diagnosis before teaching: Assess student's current understanding before presenting new material.
  • Progress checkpoints: Celebrate module completion. Use simple language. Show visible progress.
  • Session summary: Write session summaries to {wiki_root}/raw/studies/ when requested.
  • Interruption handling: Gracefully handle student interruptions. Resume from last checkpoint.
  • Learning style diagnostic: First-run gate stores optional learning-style profile in {user_context_root}/sb-tutor/step-01-boot.yaml.
💰 Finance Module

Personal finance system: monthly expense/investment closing with gatekeeper rules, investment reasoning with read-only invariants, decision recording, and tool building.

/sb-bookkeeper Command
▼

Trigger: User runs /sb-bookkeeper to conduct monthly financial close.

Purpose

Monthly financial close — gastos (expenses), investimentos (investments), or both in sequence. Active-agency gatekeeper that reads transaction/ledger data ONLY through registered tools and enforces structural invariants.

Three Gatekeeper Rules (Always-On)

Rule A — Refusal-on-Out-of-Structure: Refuse to operate on inputs/situations that do not match existing structure. Surface deviation and route resolution back into durable structure (new config entry, new mapping, new parser, append-only correction row).

Rule B — Deviation-to-Structure Protocol: When encountering unrecognized bank file, supplier with no mapping, tag that does not exist, transaction that does not fit category, or rate shape classifier cannot resolve, do NOT improvise. Surface to user and route resolution into durable structure. Dispatch to tool-builder or doc-maintainer companions as needed.

Rule C — Hybrid Issue-Surfacing: Surface blocking issues (Rule A refusals) and deferrable review-mode items separately. Provide manual bridge for user to resolve or escalate.

Activation Flow

  1. Load runtime: Read gatekeeper-loop.md — active-agency runtime protocol (three gatekeeper rules, per-step checkpoint).
  2. Load standing rules: Read {CONFIG_DIR}/standing-rules.yaml for communication language and batch UI settings.
  3. Onboarding check: Read {CONFIG_DIR}/sources.yaml. If missing or empty, route to step-00-onboarding.md.
  4. Ask flow choice: "Which flow? [1] Gastos / [2] Investimentos / [3] Both / [4] Review"
  5. Ask month: "Which month? (e.g., 2026-03)"
  6. Create directories: Ensure {RAW_DIR} and {INV_RAW_DIR} exist. Warn user if created and ask for confirmation.
  7. Route to step 1: Based on flow choice, proceed to gastos/step-01-preflight.md or investimentos/step-01-preflight.md.
  8. Chain on ambos: When gastos flow finishes (Step 08), if flow is ambos, proceed to investimentos/step-01-preflight.md.

Modes

Mode Description Steps
gastos Monthly expense close. Ingest bank statements/credit-card invoices, normalize through per-bank parsers, categorize transactions, two-pass human review, produce report, update dashboard. 8 steps under gastos/
investimentos Monthly investment close. Ingest broker/exchange files, append to append-only ledgers, recompute positions/portfolio snapshot, validate against statements, report. 8 steps under investimentos/
ambos Both modes in sequence. Gastos runs to completion, then chains into investimentos. 16 steps total
revisao Review mode. Re-evaluate already-closed months. Separate workflow: review-mode.md Specialized workflow

Tools-Only Data Access (Architectural Invariant)

The loop NEVER reads a ledger CSV, portfolio.json, or a raw source file directly. It reads that data ONLY through registered tools in ../../scripts/tools-index.md (e.g. sample_from_ledger, query_corrections, position_summary). The invariant applies equally to WRITES — all mutations MUST go through registered write tools (e.g. apply_review_resolution, rename_tags).

Companion Delegation

  • tool-builder — Builds new tools when gatekeeper needs capability tool layer does not provide. Output is tools only; never writes ledgers/portfolio/dashboard.
  • doc-maintainer — Keeps workflow documentation current as workflow changes. Reconciles durable-structure changes into docs.

Critical Rules

  • Communicate in communication.language from standing-rules.yaml.
  • NEVER skip steps. Each step ends with STOP and wait for confirmation.
  • If script fails, report complete error and ask how to proceed.
  • Credit card invoice transactions are NEGATIVE (money outflows).
  • IOF is separate transaction — never merge with original purchase.
  • Investment ledgers are append-only — never delete or modify existing rows.
/sb-investor Command
▼

Trigger: User talks to /sb-investor in natural language. Agent infers which capability(ies) to run and chains capabilities for multi-intent asks.

Purpose

Read-only investment-reasoning agent — infers intent and routes to thesis, research, review, portfolio, decision, or policy. Never mutates ledgers/portfolio/dashboard. Delegates persistence to scribes and tools.

Six Capabilities

Capability Description Persistence
thesis (B1) Turn informal investment idea into structured, falsifiable thesis sb-fin-create-thesis skill
research (B2) Discover, propose, capture, auto-file OPEN-web sources for thesis/question Registered tool: investment_source_capture
review (B3) Re-evaluate existing thesis against new evidence (staleness, evidence-against, invalidation) sb-fin-create-thesis extend mode
portfolio (B4) Map belief to real exposure (positions without theses, theses without exposure, concentration) Read-only via registered tools
decision (B5) Record buy/sell/hold/pass outcome and reasoning as dated page sb-fin-create-decision skill
policy (B6) Read or update user's research-policy.md / source-policy.md Thin mode inlined in sb-investor-loop.md

Intent Routing (Key Divergence from sb-bookkeeper)

INFER capability from natural-language ask. NEVER ask "which mode?" There is no numbered menu. A single ask MAY span several capabilities; route to ALL matching modes in dependency order. Ambiguous single-vs-multi intent is surfaced for confirmation, never guessed.

Activation Flow

  1. Load runtime rulebook: Read sb-investor-loop.md — always-on agent-loop protocol (read-only/tools-only invariants, own-workspace boundary, watchlist invariant, policy read-rules wiring, present-and-confirm, issue-surfacing, Rule A, per-step Investor Checkpoint).
  2. Load routing map: Read capability-manifest.md — maps intent → capability → access mechanism, with per-capability inputs and when-to-use/when-NOT.
  3. Infer capabilities: Parse user's natural-language ask against capability map. Select ALL matching capabilities. Order per multi-mode chaining rules. Surface ambiguous scope via present-and-confirm.
  4. Execute capabilities: For each routed capability, reach it by its Access mechanism (invoke skill, read-and-follow workflow, or call registered tool). Load Inputs. Execute under the loop. Every capability's user-facing STOP is an Investor Checkpoint.
  5. Handle unimplemented capabilities: If access-mechanism file does not exist, tell user capability is reserved but unimplemented. Stop on that branch. Other routed capabilities proceed.

Always-On Invariants (from sb-investor-loop.md)

Read-Only Invariant: NEVER mutate ledgers, portfolio.json, or dashboard. Read position data ONLY through registered read tools.

Tools-Only Invariant: Agent reasons; scribes (sb-fin-create-thesis, sb-fin-create-decision) and tools persist. Agent NEVER hand-writes thesis, decision, or raw source file.

Own-Workspace Boundary: Writes restricted to .user/finance/investor/, thesis scribe, decision scribe, and raw capture tool.

Watchlist Invariant: Any page MAY carry watchlist: true, but the agent MAY set it ONLY after explicit user approval.

Present-and-Confirm Pattern: Before any consequential action, present findings/reasoning and confirm with user. Optional [R] adversarial-refuter branch available for challenging reasoning.

Multi-Mode Chaining Examples

User Ask Chain
"review my X thesis vs today's earnings and check my position" review → portfolio
