sb-tutor — the private-tutor workflow

A guided-learning agent that teaches any subject in small, one-concept-at-a-time pieces — first profiling what you already know, grounding lessons in your own notes when it can, and logging knowledge gaps back into your wiki as it teaches.

⚑ What to review — flags first

These are the points worth your attention before you trust this workflow as-is. Everything below this block is the faithful map of how the workflow actually behaves; these are the tensions, risks, and one nice safety property I want you to confirm or correct.

🔴

Cross-module coupling: the --queue-file flag is load-bearing and easy to drop

When the tutor researches a new source, it MUST pass --queue-file study-queue.md on the capture command — even on the normal open-web path where the flag does nothing on success. The reason: if a source unexpectedly gets blocked (403 / bot-wall) and the flag is missing, the blocked-source row lands in finance's source-queue.md instead of the wiki's study-queue.md, "breaking finance byte-identity." That is a silent, hard-to-notice failure mode wired across two modules.

Source: step-01-boot.md → Research-and-Enrich Procedure, step 3
🟡

Wiki search runs on every single subject — including tangents and mid-lesson questions

The "Mandatory Wiki Check" (C6) fires before answering any subject the student raises — the brought topic, a picked menu item, a mid-lesson question, even a tangent. Each fire runs a Python search call. Faithful to the design, but worth confirming you want that cost/latency on throwaway tangents, not just on real lesson topics.

Source: step-01-boot.md → C6 + Mandatory Wiki Check
🟡

The "is this note good enough to teach from?" bar is fuzzy

Whether a lesson grounds in your notes depends on a relevance score clearing a "grounding bar." The bar is defined only as "at or above the helper's mid-range" and is called "empirical and tunable." There is no concrete number, so behavior can drift between runs of the search tool. Confirm whether that vagueness is acceptable or should be pinned to a fixed threshold.

Source: step-01-boot.md → C7 / Mandatory Wiki Check outcome B
🟡

The study queue has no janitor — the tutor itself must clean up

When a blocked/gated source is later resolved, the tutor must manually remove its row from study-queue.md ("the study queue has NO automated lint steward"). If a session ends before resolution, that row lingers with no process to retire it.

Source: step-01-boot.md → Research-and-Enrich Procedure, step 6
🟡

First-run setup keys on its own entry, not on the file existing

Both startup gates (paths + learning style) decide "first run?" by checking for their own specific entry inside the profile file — not by whether the file exists. This is deliberate (the file may already hold other entries), but it's subtle: a partially-populated profile can still trigger one gate and skip the other. Worth confirming this is the intended behavior.

Source: step-01-boot.md → Bootstrap, Gate A & Gate B
🟢

Nice safety property: your notes are never treated as ground truth

The workflow is explicit that your wiki is "the owner's partial synthesis, NOT the correctness authority." On a contradiction it must surface both ("your notes say X; the general understanding is Y") and flag it — never teach a wrong note back to you as fact. Good guard against compounding your own errors.

Source: step-01-boot.md → C4 / Mandatory Wiki Check step 3

1 How the three files fit together

Invoking the tutor walks a short chain: a thin command points to the persona, which points to the one big rules file. There is intentionally no "step 2" — once booted, the tutor just runs continuously in teaching mode.

Command — sb-tutor.md
A one-line loader. Its only job: "read and execute the persona file." This is the thing you trigger.
Persona — sb-tutor.md (workflow)
Sets the identity ("private tutor, any subject") and tone (warm, patient, never condescending), then says: load the boot step, and route on whether you brought a topic.
Boot step — step-01-boot.md
The whole brain. Loads every behavioral rule for the entire conversation: first-run setup, how to use your notes, the wiki check, and the 10 teaching rules. ~25 KB — everything else is here.
Continuous pill mode
No further steps. The tutor teaches one small concept at a time, pausing after each, until you stop.

2 First-run setup — two independent gates

On its very first run for you, the tutor saves a few things once and reuses them forever. It runs two separate checks, in order. Each checks for its own saved entry, so one can run while the other is skipped.

Gate A  Where things live

Triggered only if your profile has no "study topics" / "summary destination" entry yet.

  • Asks: where to find study topics when you don't bring one (a markdown file, or none).
  • Asks: where to write session summaries (a folder, or none = chat only).
  • Appends both answers to your profile YAML. read topics · write summaries
  • Never rewrites or removes any existing entry.

Gate B  How you learn

Triggered only if your profile has no pref.learning.profile entry yet.

  • Runs a quick 10-question learning-style diagnostic (from a shared prompt file).
  • Figures out your primary/secondary learning style + environment needs.
  • Saves it as a new entry telling future runs how to pace and explain for you.
  • Never overwrites your existing style preferences — both coexist.

Your saved profile already exists (diagnosed 2026-06-13): visual-primary, auditory + kinesthetic secondary, "big-picture first then details, briskly." So on your machine both gates are satisfied and skipped — the tutor goes straight to teaching.

3 The Mandatory Wiki Check — grounding every subject

Before answering any subject, the tutor runs one deterministic search against your knowledge base and branches into exactly one of four outcomes. Training-data knowledge is always the teaching substrate; the wiki's job is to personalize/ground it and to surface gaps — never to be the final word on what's correct.

python {sb_os_path}/wiki/scripts/sb-wiki-search.py search "<subject>" --k 5 --json

Always called first. Reads the JSON envelope (available / mode / results). If the tool is missing or crashes, it degrades to a plain text search — never hard-fails the lesson.

A Unavailable

No wiki installed. Teach from general knowledge; tell the student once that grounding is off. Do not log a gap (nothing to gap against).

B Strong hit

Top result clears the bar. Ground the lesson in that page, cite it by subject (never the filename), blended with simple language + your learning profile.

C Weak / no hit

This is the gap signal. Teach from general knowledge with no fake citation, AND run the Gap Handling procedure (next section). A miss is normal, not an error.

D Degraded

Keyword-only mode (e.g. semantic search key missing). Proceed on the keyword results as if A/B/C — never hard-fail.

🟢

Contradiction handling (outcome B)

If a grounding page contradicts current/general understanding, the tutor must surface both and flag it — it never teaches your note back to you as authority. (Same property called out in the green flag at top.)

4 When your notes have a gap → log, then optionally research

Outcome C (weak/no hit) means your wiki is missing something. The tutor handles this in two layers: an unconditional floor that always logs the gap, and an owner-gated offer to go research and fill it — which only runs if you say yes.

Floor — always logs the gap
Appends one entry to questions.md: a dated question + links to any near-miss pages. Runs even if you later decline research and even if web tools are unavailable. No fetching yet.
Offer — asks first, always
"Want me to research sources on this to add to your wiki?" Never captures or fetches before you approve.
Decline → continue
Gap stays logged; lesson continues from general knowledge. Nothing further happens.
Approve → research → capture → auto-ingest → report
Finds candidate sources, you pick which to keep, each is captured into raw/, auto-ingested into wiki pages via /sb-wiki-ingest silent, and reported back by subject.

5 When you bring no topic — the menu

Invoked empty, the tutor builds one merged menu of what you could learn today. This is the only place it enumerates from your knowledge base by listing index files (not the search tool, which needs a query). A pick then enters diagnosis exactly like a topic you brought in.

① Open questions (first — studying one retires it)

From open-gaps.md, falling back to questions.md.

② Topics

From the topics index — each row's scope is a candidate.

③ Theses finance only

Only shown when the finance extension is installed; otherwise silently omitted.

④ Your static list

Your learning-topics.md — augmented, never replaced. Capped ~5 per group.

Edge cases: empty wiki → show the static list only. Both empty → just ask what you want to learn. A missing index file is skipped silently, never aborting the menu.

6 The 10 teaching rules

These govern every pill. Filter by what they control.

All 10 Pacing Diagnosis & plan Language Checkpoints & recap
R1

Digestible pills

Max 20 lines of prose, one concept per response. Code-heavy topics may add a ≤15-line snippet — always explained.

R2

One pause per response

End every pill with one prompt: did you understand / restate it / a reflection question. Never advance unprompted. Wrong answers get a different angle, not a repeat.

R3

Diagnosis before teaching

Never teach cold. Probe 5–10 key terms (3 at a time: know / heard of / no idea), then ask your goal. Calibrate start, depth, focus.

R4

Plan before execution

Present a 5–7 module learning plan and let you adjust before starting.

R5

Visible progress

Every pill carries a header: [Module X of Y — Name].

R6

Module checkpoint

At each module's end: 1–2 challenge questions, a 3–5 line recap, and "related topics you might explore."

R7

Simple language

Everyday analogies; define any technical term in one line before using it.

R8

Never assume

Ambiguous question → ask what you meant. Never assume your level without diagnosing.

R9

Session summary

Only when a full R4 plan completes: write a substance-rich reference document (real definitions and distinctions, not a table of contents), grouped by concept. Saved as a new dated file or shown in chat.

R10

Handle interruptions

Tangents answered briefly then offered a return; "skip ahead" jumps and states what's skipped; a new topic bookmarks the old and re-diagnoses; "I already know this" → quick confirm then skip.

8 What one "pill" looks like

The fixed shape of every teaching response.

[ Module 2 of 5 — How a knowledge graph stores facts ]

A knowledge graph stores facts as relationships between things, not as rows in a table. Think of each fact as a tiny sentence: subject → relationship → object — "CUDA → made-by → NVIDIA." Each thing is a dot (a node), each relationship is an arrow (an edge) connecting two dots.

(≤ 20 lines, exactly one concept. A code snippet ≤15 lines could sit here, always explained.)

Can you tell me, in your own words, what the arrow between two dots represents?

9 Things the tutor must never do

The explicit "never" list — the boundaries of the behavior above.

  • Deliver more than one concept per response
  • Advance without waiting for your response
  • Start teaching without running diagnosis
  • Use long paragraphs — prefer lists and short sentences
  • Ignore your question to "maintain the flow"
  • Use context files for topics they don't cover
  • Cite filenames — always refer to content by subject
  • Repeat the exact same explanation when you didn't understand
  • Drop a code block without explaining it
  • Be condescending when you struggle
